# ICT Deployment Standards

**Last reviewed:** 2026-11-13 · **Owner:** Operator, with the DPO

What must be true of the operator, the hosting, the vendors and the way we release before this service is deployed to the public in the Philippines. The step-by-step technical checks are in [06-operations/deployment-security.md](../06-operations/deployment-security.md); this page sets the standard those checks enforce.

> Government ICT rules (DICT circulars, the National Cybersecurity Plan) bind government agencies, not us. We follow the relevant parts by choice. The Data Privacy Act parts are binding.

## 1. The operator must be a legal person (D-16)
Today the service is run by an individual with no registered business. That blocks three things: registering with the National Privacy Commission, signing a processor agreement, and having counsel sign off a named controller.

| Step | With | Needed for |
|---|---|---|
| Choose a form: sole proprietorship or one-person corporation | Counsel's advice (liability differs) | Everything below |
| Register the business name or company | DTI (sole proprietor) or SEC (corporation) | Legal identity |
| Tax registration | BIR | Lawful operation, even with no revenue |
| Local permits | Barangay and city or municipality | Lawful operation |
| DPO registration, if a threshold applies | NPC | [Matrix A-07](compliance-matrix.md) |

A beta shared privately with testers can run before this. A public launch (M8) should not.

## 2. Hosting and data location
| Standard | Our state |
|---|---|
| Data is classified before hosting is chosen | Done: classes C0 to C3 in the [data inventory](data-inventory-and-retention.md) |
| The region is chosen on purpose and recorded | Singapore, set in `render.yaml` (D-13). Closest region to Philippine users |
| Cross-border transfer is disclosed | To be stated in the privacy notice; recorded in the PIA |
| No law requires us to host in the Philippines | Correct for a private service today (◻ counsel to confirm). We stay accountable wherever the data is (RA 10173 Sec 21) |
| All components sit in one region | The safety ledger (M6) must use the same region as the app |
| No user data in development or CI | True: tests use generated data; GitHub holds code only |

**Free-tier risk.** Render's free plan has no uptime commitment, sleeps when idle, and offers limited log control. That is acceptable for a beta. Before M8, confirm in writing what the plan gives us for log retention and a processor agreement, and move to a paid plan if it gives neither.

## 3. Vendor due diligence
Before any vendor touches user data, answer these and file the answers.

| Question | Render | Database provider (M6) |
|---|---|---|
| What data will it handle? | All traffic; edge logs | Safety ledger |
| Where is it processed and stored? | Singapore | Must match the app |
| Is there a data processing agreement? | To obtain (G-05) | Before first use |
| Recognised security certification (ISO 27001, SOC 2)? | Verify and record | Verify and record |
| Does it notify us of its own breaches, and how fast? | Check the agreement | Check the agreement |
| How long does it keep logs and backups? | Verify (V-01) | Set to 7 days |
| Who are its sub-processors? | Record | Record |
| How do we get our data out and deleted when we leave? | Record | Record |

Adding a vendor that handles user data is a change to the [data inventory](data-inventory-and-retention.md) and needs the DPO's approval.

## 4. Environments
| Environment | Purpose | Data | Secrets |
|---|---|---|---|
| Local | Development | Generated only | `.env`, never committed |
| CI | Tests, scans | Generated only | None with production access |
| Production | Real users | Real | Platform secret store only |

There is no staging environment today. Before M6, when a database with real records arrives, add one that never shares secrets or data with production.

## 5. Security baseline
The baseline is NPC Circular 2023-06 for personal data, with OWASP ASVS as the technical yardstick. The controls are listed and tracked in the [security checklist](../04-security/security-checklist.md) and the [threat model](../04-security/threat-model.md). The minimum for any public deployment:

- TLS everywhere; HSTS; strict CSP with no inline script
- Every input validated at the server boundary; payload cap; rate limits
- WebSocket origin allowlist; short-lived connection token
- No content, keys or raw IPs in logs
- Secrets generated by the platform, rotated on a schedule and after any suspected exposure
- Dependencies pinned by lockfile; high-severity advisories block the build
- Secret scanning and static analysis on every pull request

## 6. Access
Detail: [roles-and-access.md](roles-and-access.md).

- MFA on GitHub, Render, the database provider and the domain registrar
- No shared accounts; each person has their own
- Least privilege; production access limited to the operator role
- Access reviewed every quarter and when anyone leaves
- A second trusted person can act if the operator is unreachable (bus factor: today it is one)

## 7. Change and release
- Every change to `main` goes through a pull request with green CI and owner review of security-critical paths
- Deploys happen only after CI passes; the previous build can be restored in one step
- Each milestone release passes its [compliance gate](compliance-gates.md)
- A change that touches personal data updates the data inventory in the same pull request
- Releases are tagged; the change log says what changed for users

## 8. Logging and monitoring
- Structured logs with correlation ids; no personal data beyond a hash prefix
- Log retention known and documented (V-01)
- Uptime check on `/health`; alerts go to a named person
- Detail: [monitoring-observability.md](../06-operations/monitoring-observability.md)

## 9. Continuity
- Nothing durable exists before M6, so recovery is a redeploy
- From M6: encrypted backups, 7-day retention, restore tested, purge re-run after any restore
- Rollback rehearsed once before launch
- Detail: [disaster-recovery.md](../06-operations/disaster-recovery.md)

## 10. Who we tell when something goes wrong
| Event | Tell | Deadline |
|---|---|---|
| Personal data breach | National Privacy Commission; affected users | 72 hours ([procedure](breach-notification.md)) |
| Child abuse or exploitation | PNP or NBI | 48 hours ◻ ([procedure](child-protection-and-online-safety.md)) |
| Cybercrime against us (intrusion, extortion) | PNP Anti-Cybercrime Group or NBI Cybercrime Division | Promptly |
| Significant security incident | National CERT (DICT) | Promptly, by choice |
| Vulnerability reported to us | Reporter gets an acknowledgement | 3 days (`SECURITY.md`) |

## 11. The public face
- A custom domain owned by the legal entity, with registrar lock and MFA
- Privacy notice, terms and rules reachable from every page and before the gate ([public-policies.md](public-policies.md))
- Plain language. Consider a Filipino version of the gate, rules and privacy notice for the Philippine beta
- DPO contact published
- Accessible to WCAG 2.1 AA where practical (keyboard use, contrast in all four themes, screen-reader labels). Checked in M7

## 12. Scope of the first launch (D-18)
The plan is a **Philippines beta**. Decide how that is enforced: by invitation only, by a country allowlist using the M5 lookup, or not enforced and only stated in the terms. Recommendation: country allowlist plus the terms, so that one legal regime applies while moderation capacity is small.

## 13. Go-live checklist
Run on the live URL, with evidence kept:
- [ ] Legal entity registered; DPO and child-safety officer named
- [ ] All gates through M8 in [compliance-gates.md](compliance-gates.md) are green
- [ ] Post-deploy smoke test in [deployment-security.md](../06-operations/deployment-security.md) passes
- [ ] Vendor answers in section 3 filed
- [ ] MFA screenshots and first access review filed
- [ ] Counsel's sign-off on file
